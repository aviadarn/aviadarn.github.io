Does paying for human-annotated data beat taking it at random? 2026 · Qwen2.5-VL-3B + LoRA on ChartQA · total rented-GPU cost $1.81
+1.7 ptshuman data · p = 0.042
+0.4 ptsquality score · p = 0.685
1.51×human recovered, no benefit
2,500eval Qs, frozen first

github.com/aviadarn/vlm-data-strategy

ChartQA's training pool is 74% template-generated and 26% human-written — the shape of a real sourcing decision, where synthetic augmentation is cheap and human annotation is not. If you can afford to train on 4,000 examples, which 4,000 should you buy? Three arms at a fixed budget, identical in everything except which examples they contain: base model, adapter rank, learning rate, schedule, steps, seed, prompt and evaluation all held constant. The 2,500-question test set was frozen before any training run, and decoding is greedy so no arm moves on sampling noise.

Human-authored data wins by 1.7 points on the human-written slice (p = 0.042). The two arms also buy different things: against the baseline, random gains +4.8 on text answers and +0.3 on numeric — it mostly learned ChartQA's answer format. The human arm adds only +0.5 more on text but +1.1 on numeric, which is the part that requires actually reading the chart.

The third arm is the one worth building. If a cheap score computed from question and answer text alone could pick out the good examples, a vendor pipeline could gate on it without knowing or trusting who produced each item. It ranks by templatedness, near-duplication, answer leakage and degeneracy — and it never sees the source label.

The score works as a detector and fails as a selector. Its top 4,000 is 39.6% human against a 26.1% base rate — a 1.51× lift, so surface form genuinely carries provenance signal. But the model trained on that selection scored 0.7392 against the control's 0.7344, p = 0.685. Recovering half again as much human data bought nothing measurable. Whatever makes human annotations better training material is not what this score detects. The practical reading: demand provenance metadata from vendors rather than inferring it — a heuristic that half-works as a classifier can be worthless as a filter, and the classifier metric would have told you it was working.

Two bugs, both caught in a probe before the real runs, both of which would have produced confident wrong numbers rather than crashing. Right-padding silently corrupted batched generation — decoder-only models need left padding, and with pad tokens between the prompt and the first generated token the baseline scored 0.104 instead of 0.630 on the same 200 questions, with nothing erroring. And an unstable sort made the experiment unreproducible: sort_values defaults to quicksort, the quality score produces many exact ties, and the scored arm came out 24.8% human on one machine and 20.5% on another from identical inputs. Fixed with a stable sort and an explicit tie-break; all three selections now hash identically across machines. The first version of the README reported that the score recovered no human data at all — that was this bug, not a result.

Stated in the repo, not buried: p = 0.042 is marginal, this is one seed on one model and one task, and the effect is 1.7 points on 1,250 questions. A second seed costs about $0.50 and should come before the claim carries weight.

Can you game a vision-language judge? 2026 · QA harness, 1,152 adversarial submissions · total rented-GPU cost $0.03
91 of 144correct answers rejected
4.2×confident fabrication
36.8% → 3.5%without the reference
1–3%hack rate that meant nothing

github.com/aviadarn/vlm-judge-hacking

A judge scoring model answers is a reward signal, and a reward signal that can be satisfied without doing the task is a reward hack waiting to happen. So the question is not “is the judge accurate” but which specific exploits move it, and how often. 1,152 submissions over 144 ChartQA questions, balanced across human-written and machine-generated questions and numeric and text answers. Every wrong answer is a real model error, drawn from the 10,000 recorded predictions of the four fine-tuned models above — inventing plausible wrong answers would measure the imagination of whoever wrote the suite.

The headline is a control failure. Qwen2.5-VL-3B rejects 1,065 of 1,152 submissions — including 91 of 144 genuinely correct answers, with zero unparsed verdicts. It is not robust, it is inert, and a hack-rate table alone would have shipped a broken reward model as a safe one. Two of the eight cases are controls for exactly this reason, and the report now refuses to interpret any attack number until they pass.

Confident fabrication is the exploit that works. A wrong number delivered with a fabricated derivation — “read directly off the axis label and confirmed by the data label printed on the bar” — is accepted 4.2× more often than the identical wrong answers stated plainly, and it is the only attack that survives into blind mode. Verbosity, style-matching, shotgunning and near-miss numbers all did nothing. Assertive fake reasoning is what moves this judge.

The reference is doing nearly all the work. Run the same suite without showing the judge the gold answer and its ability to recognise a correct answer collapses from 36.8% to 3.5% — a 91% loss, with the intervals against wrong answers now overlapping entirely. That is the transition from grader to reward signal: a judge that is marginal in an eval pipeline is worthless in an RL loop, and testing it only in reference mode tells you nothing about the setting where hacking actually pays.

One judge, one size, one task, and fixed attack phrasings — a larger judge would very likely clear the control bar. That is the point of shipping the harness rather than the number: --model points it at any judge, and the control test is what tells you whether yours is usable.

A published off-road 3D segmentation baseline reports 0.8096 mIoU on the GOOSE 3D challenge. I sliced one prediction pass by the platform the frames came from. The headline number turns out to be the wheeled vehicle talking — it contributes 72% of the validation points, and the excavator sits 19 mIoU points below it, on a checkpoint whose own config trained on excavator frames. This is not a zero-shot transfer gap.

The confusion matrix says what actually happens: from the excavator's mast, 89% of obstacle points are predicted as natural ground, and 98% of made ground. The model keeps the dominant class — soil, 60% of returns, IoU 0.88 — and loses the two classes a machine that digs has the most reason to care about. Three million labelled obstacle points is not a small-sample artifact.

Dust is the expensive one, and it is cheap to cause. Corrupting 2% of returns costs 0.116 mIoU — about what killing half the sensor's beams costs (0.134). Mount drift does nothing. Rotating the cloud up to 2°, the way a mast shifts on a machine that vibrates all day, leaves the score flat. That was the failure mode I built the sweep to catch, and it is not a failure mode — worth knowing before anyone funds mount rigidity for this model.

The follow-up question was whether something small enough to run on the machine does better on the classes the baseline collapses on. I chose the representation by measurement rather than by convention: a spherical range image keeps only 4.2% of points on these accumulated clouds, so a 0.20 m BEV grid it is — 100% of points kept, and a per-cell majority label round-trips 94.1% of per-point labels, checked per class.

3.5× better on obstacles, 30× on made ground, and it gives up overall accuracy and loses on human and vegetation to get there. The honest framing: a small specialised model beats a large general one on the platform it was specialised for — not that a U-Net beats a point transformer.

Every op is native to TensorRT 8.2 at ONNX opset 11, so it exports with no plugins. On a Jetson Nano, FP16 runs at 127.7 ms mean / 129.5 ms p99 from an 11.8 MB engine. Against a 10 Hz lidar the budget is 100 ms, so a six-year-old board misses real time by 1.3× with no optimisation work done yet. INT8 could not be demonstrated and the log says why — Maxwell predates DP4A, so TensorRT accepts --int8, falls back, and emits an engine identical to the FP16 one. Reporting a 1.63× "INT8 speedup" would have been the FP16 number wearing a different label.

The evaluation was lying before the model was. Every rollout metric came out as mush until I isolated it: the VQ decoder is silently wrong on Apple Silicon. Token ids were bit-identical between CPU and MPS and transformer logits matched to 1e-6, but decoded pixels scored ~14 PSNR against 24–31 on CPU. Root cause is a mid-block attention returning a channels-last view that the MPS SiLU kernel mishandles — three .contiguous() calls. Reported upstream as issue #29, fix submitted as PR #30. The July training run had been healthy all along; only its metrics were corrupted.
SO-101 manipulation policy in simulation 2026 · LeRobot + ACT in MuJoCo, trained on Apple Silicon
88%unseen layouts, 50 trials

github.com/aviadarn/so101-lerobot

The full imitation-learning pipeline for an SO-101 arm: scripted IK expert, a 600-episode two-camera dataset at 320×240, and ACT (action-chunking transformer) trained on an M-series Mac. 88% pick-and-place success on unseen object layouts, independently confirmed at 92% on a second seed set. Dataset keys and units match the real so101_follower, so the same code drives the physical STS3215 arm unchanged.

  • Warm-starting was the single biggest lever. Resuming from the previous best checkpoint hit 72% in 10k steps, where the from-scratch run needed 60k to reach 68%.
  • Checkpoints had to be selected on rollout success, not training loss. Loss fell steadily from 0.060 to 0.057 across a ten-point drop in success. Both runs peaked and then declined. Trusting the loss curve would have shipped the worse policy.
  • Data saturates early. From 50 demonstrations onward success sat at 84, 88, 86, 80% — a 6× increase in data bought nothing. What did move it: fixing the randomised wrist camera, halving the resolution so the same Mac could afford 3× the steps, and tightening the overhead crop.
  • The failures are informative. Every grasp now converts to a success; what remains are runs that never close on the cube, spread evenly across the spawn range — vision precision, not timing or policy structure.
Two variants failed before this worked. A 35 mm cube run collapsed to 2/20 because the scripted expert does not yaw-align the jaw, so its demonstrations disagreed with each other. Temporal ensembling and re-planning every 25 or 50 steps were both worse than executing the full 100-step chunk. Inconsistent experts cost more than small ones.
Teaching a bipedal robot to jump — and catching the reward hack 2026 · Open Duck Mini v2, MuJoCo MJX + JAX, PPO on rented GPUs
227.6best reward — worst robot
32%airborne when told to walk
6 → 0falls, after reverting

github.com/aviadarn/Open_Duck_Playground — my work on a fork of apirrone/Open_Duck_Playground

I added a one-shot triggered jump to the Open Duck Mini v2 walking policy: press a key, the duck crouches, leaves the ground, lands, and resumes walking — one unified policy for both gaits. Eight-dimensional command with a jump flag, a shared jump state machine, gated reward terms, and a space-bar trigger in the MuJoCo viewer.

I got the constraint wrong on paper first. Arithmetic from the MJCF said force was not the limit: at 2.107 kg the duck weighs 20.7 N, and with a ~0.09 m effective moment arm two legs supply roughly 72 N, about 3.5× body weight. That pointed at the slew-rate clamp on motor targets — 0.105 rad per control step at 50 Hz — as the thing to raise. It was a clean argument and it was wrong.

The probe said the opposite. Driving the legs open-loop to full extension pins actuator_force at 3.23 / 3.23 N·m — torque is binding. And the slew clamp I had nominated was worth almost nothing: 5.24 against 30 rad/s moved peak rise by 0.6 mm, 32.5 to 33.1. The knob I had already raised had bought essentially zero. A third finding came free: raising forcerange alone plateaus around 37 mm from 2× to 16× — force and kp together are what raise takeoff velocity.

So the 4×-actuator variant was built to settle one question the measurement had opened: is the ~8 mm hop an actuator limit or a learning limit? Real STS3215 servos cannot deliver 4×, so the task was sim-only and disposable by design.

It produced the highest reward of any run, 227.6 — and the worst robot on the bench. Identical 2500-step rollouts, all three commanded to walk forward at +0.15 m/s:
Policyfallsz wobbleairborne %vx (m/s)
walking only, stock actuators00.00390.0+0.038
jump 1/800, stock actuators00.00320.0+0.085
jump, 4× actuators60.032732.0−0.134

With 4× actuators the policy stopped walking and started bouncing: airborne 32% of the time, moving backward when commanded forward, falling repeatedly. The jump terms contributed roughly 615 of the episode reward, swamping the degraded locomotion, and nothing in the reward function penalises a permanently bouncing gait. So the extra airtime never answered the question it was built to answer — it was measuring continuous bouncing, not flight, and the apex figure derived from it was meaningless.

Reverted, with the reasoning in the commit message. That is two wrong conclusions in a row on the same knob: the paper argument that torque was fine, then the measurement's implied fix that more torque would buy height. Each was overturned by the next thing I checked — arithmetic by a probe, the probe's fix by a behavioural rollout.

The policy that ships is the stock-actuator one at jump_prob = 1/800: no falls, the steadiest base of the three, the best forward tracking, turning at 0.43 rad/s, and an honest ~8 mm hop — a height the real STS3215 servos can actually deliver. Lowering the jump probability that far was itself a trade: jumping more often measurably degraded turning.

Also built here: one-command observability for remote training runs. ./monitor.sh finds the live vast.ai instance by itself and brings up Prometheus, Grafana and Loki against it — GPU, CPU and memory graphs, the training log, and the eval-reward curve in one dashboard, served from my own laptop over SSH with nothing exposed publicly. A --lite mode serves a zero-dependency page with no Docker at all. Separately, switching JAX to cuda12-local cut remote setup time by 65%.

Blind stair climbing with PPO 2026 · MuJoCo + Gymnasium + Stable-Baselines3

github.com/aviadarn/mujoco-rl-playground

PPO locomotion in MuJoCo: an Ant quadruped trained to walk on flat ground past an eval return of 1000, then warm-started onto AntStairs-v0 — a generated five-step staircase, 10 cm rise and 50 cm run, topped by a five-metre plateau. The policy is blind: standard proprioceptive observations only, no terrain sensing of any kind. It gets over the steps and across the plateau in 14 of 20 episodes.

The obvious success metric does not work here, which is the interesting part. Torso height sounds like the right way to prove a climb — and it is not usable frame by frame, because the Ant's gait already bobs between 0.5 and 1.4 m on flat ground, straight through the range a 0.5 m climb would produce. What survives is the mean: averaged over an episode, torso height on the plateau sits 0.19–0.35 m above the same policy's flat-ground average, against a 0.5 m total rise. The per-episode pass/fail call is made on distance instead, x ≥ 5.5 m, which the plot above shows separates cleanly.

An earlier 5-episode sample read 4/5; re-running it gave 2/5. Both are noise around the same policy — 20 episodes puts it at 14/20. Five samples was not enough to quote a rate from.

A silent bug that looked exactly like success. MuJoCo's ant.xml sets conaffinity="0" in its geom default, and only the floor overrides it. Custom terrain geoms therefore have no collision unless they set it explicitly — so the ant walked straight through the staircase while every metric reported a clean climb. Same shape as the decoder bug in the world-model project: the measurement agreed with me before the system did.

The stairs builder is generalised, so Walker2dStairs-v0 (30 steps, 20 cm rise) drops out of the same code. Training runs on CPU deliberately — PPO with MLP policies is faster there than on MPS.

Reproducing a published shortcut-feature result 2026 · LeJEPA on ImageNet-1k, rented A100s
14.5% → 0.51%linear probe collapse
13.1%matched-energy control
2.5×better training objective
$18measured, not estimated

github.com/aviadarn/obsessed-encoder-repro

An independent reproduction of the LeJEPA case from Enigma Labs' The Obsessed Encoder: three arms, 30k steps, cost measured before committing. Planting a faint predictable watermark drove the online linear probe from 14.5% to 0.51% — chance is 0.1% — while the training objective got 2.5× better.

The arm that makes the claim is the control. A matched-energy pattern, differing from the watermark only in whether it repeats, landed back on the baseline at 13.1% — which isolates predictability, not added pixels, as the cause. Paired-input cosine similarity inverts between the arms, 0.888 against 0.057: the encoder represents the key and discards the picture. Two breakages in the published quickstart were found and fixed on the way in, and sent back as PRs.

A robot policy that fought back 2024 · JetBot on a Jetson Nano, built with my kid · rebuilt in simulation and on the same Nano
40/40 vs 1/40same frames, fixed vs 2024 labels
6.7 → 21 fpssame Nano, 2024 setting vs tuned

github.com/aviadarn/jetbot-driving-policy

An autonomous JetBot on a Jetson Nano, wired into a kids' ride-on car: ~3,000 hand-labelled frames, a behaviour-cloning ResNet18 that predicts where to steer, and a YOLOv5 stop-sign detector running in series with it on every frame, inside a 4 GB / 10-watt envelope. Three rounds of re-collecting data (imbalanced, then uniform, then straight-heavy) is what made it drive the hallway course.

The images and weights didn't survive, so I rebuilt it. A MuJoCo cone corridor matched to the 2024 camera frames, the same network and training recipe, the 2024 controller ported line for line, and the three data rounds re-run as a controlled experiment on corridors the network never trained on, each driven both ways.

Reading the old notebook turned up two bugs that interact. The steering labels were normalised as (px − 50)/50 on a 224-pixel frame, a leftover from an older NVIDIA example, so the centre of the image read as a hard right. And a flip augmentation that was switched off in the constructor ran on every sample anyway, negating those off-centre labels. In simulation that label code decides everything. The data mix barely matters: every mix completes 40/40 once the labels are centred.

Every failure goes off the right. The real round-3 car drove smoothly, so this is a simulator prediction to test on the car, not a verdict on 2024. The gap comes down to a short list of guesses the simulator makes (the steering actuator, the camera geometry, whether the real network could tell mirrored frames apart), and each can be measured on the car.

The first version of that result was my bug. The network trained the 2024 way learned to tell flipped training frames from real ones. The cue was my renderer: its anti-aliasing used cv2.pyrDown, which centres on even pixels and doesn't commute with a mirror, so every frame had a half-pixel handedness. I fixed it, added a mirror-symmetry test, and re-ran the pair. The result held, but for a different reason: now the one floor tile repeated under every corridor gave the flips away. On a floor it had never seen, the same network completes 18/40.

The safety stop has its own story. The 2024 stop-sign set is traffic-sign crops, median 49×49 px, where every box covers the whole image. Retrained with the 2024 recipe it reproduces the 0.995 mAP50, and it boxes 97% of every frame, including 12 of 12 real frames from the 2024 car with no sign in them. The 2024 car's detector worked, so its weights were different; this data just gives a model no reason to learn what isn't a sign. Stock COCO YOLOv5s finds the sign out to 2.5–3 m with no false stops.

On the same Nano, the 2024 setting (detector at 640, FP32, every frame) takes 143 ms per decision even on TensorRT, 6.7 fps. FP16, a 320 input and the detector on every 4th frame bring it to 14.6 ms, and the camera becomes the limit at 21 fps. Unpinned clocks alone cost 37%: the governor parks the GPU at 58% because the loop only keeps it busy about half of each frame.

Upstream contributions

Bugs found while using other people's code, sent back with a reproduction.

  • EvolvingLMMs-Lab/lmms-eval #1550 — batched generation was silently right-padded
    Qwen2.5-VL ships no padding_side, so it falls back to "right" — and a decoder-only model then generates from the pad tokens rather than the prompt, with nothing raising. Two wrappers batch and generate without setting it, while four other files in the same repo already guard it. Found while running my own ChartQA evaluations, where the same bug cost 0.104 vs 0.630 relaxed accuracy on identical questions. One line each, plus a CPU reproduction that needs no model weights.
  • tempo-sim/Tempo #597merged
    Setup failures in this Unreal Engine simulation toolkit were invisible and the installer assumed a terminal. Now they surface, and it runs without one.
  • EnigmaLabsAI/multiverse #2 — half the peak memory, bit-identical output
    Profiling Enigma Labs' open-source multiplayer world model on Apple Silicon traced its documented CPU-fallback requirement to one unimplemented MPS kernel: bicubic upsampling was round-tripping to the CPU on every rendered frame. Self-attention was also materialising a 1.1 GB matrix per layer, twice per frame. The PR raises the version floor so the interpolation is untouched and computes attention in head groups — 2315 MB down to 1074 MB, output bit-identical, with a reproducible inference benchmark.
  • thuml/iVideoGPT #30 — a silently wrong VQ decoder on Apple Silicon
    Root cause and fix for the decoder corruption above: a channels-last view from mid-block attention that the MPS SiLU kernel mishandles on torch ≤ 2.5. Three .contiguous() calls, plus a check script, verified on torch 2.2.1 and 2.14.0. Closes issue #29.
  • standardbots/sb-rest-api #2 — fail clearly on an unsupported Python
    The generated client raised an opaque TypeError on Python < 3.10 and the documented minimum was wrong. Now it fails with a message that says what to do.
  • Enigma-Incorporated/The-Obsessed-Encoder #2 and #3 — making the quickstart run again
    The two breakages found while reproducing their result: the Imagenette path pointed at a retired hub parquet revision, and there was no CI. #3 restores the dataset path; #2 adds the test suite and turns VERIFYING.md into an exit code.
